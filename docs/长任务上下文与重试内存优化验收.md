## 查到的问题及实际修改

这轮继续检查并行长文任务的额外内存，发现两处与模型理解质量无关的保留：

- **调度器保留完整快照。** 注册任务读取并解码整份 `payload_json`，但路由只使用项目、对话、任务类型和手机设备 ID。序列化原文和解码副本随调度协程保留到整项任务结束。状态判断和重试等待也曾反复读取完整任务行。
- **失败堆栈保留已失败的原文。** 任务失败后，重试记录需要错误分类、原因、次数和等待时间；内存中的异常还带着已结束调用的堆栈，可能引用原文、解析列表、图片请求和模型响应。进入重试退避或暂停时，这些数据仍被上一轮尝试留住。

已作以下修改：

1. **调度器只投影归属字段。** SQLite 返回项目、对话、设备及任务类型，调度层不再解码或保留完整聊天／资料快照。完成、失败判断和退避轮询读取各自需要的状态字段。导入取消／重试单独投影原资料 ID，继续正确更新对应资料状态。
2. **生成只读取恢复所需的设置和快照。** 讲解流程从保存参数读取模式、风格、语言、审查、内部并行和冻结聊天；提取后释放序列化副本及不相关字段。真正要交给模型的冻结聊天和完整原文件仍保留，没有改成摘要或裁短原文。
3. **重试决策保存后释放失败引用。** 原有分类、HTTP 状态和 `Retry-After` 已用于保存重试状态后，再清理已结束调用的堆栈和尝试引用。包括原因／上下文链、节点失败组和异常组；次数、失败原因、部分成果和外部文件操作风险标记保持。下一次按原任务意图恢复，仍复用完成步骤。
4. **等待通读只更新阅读 ID。** 原来加载旧参数后等待，再整份回写，可能覆盖等待时新增的其他字段。现在通过 `json_set` 单独写入 `reading_id`；依赖轮询只读状态与该 ID。后来公开聊天不会替换保存的生成对话。

没有删除用户的聊天记录或资料，也没有改变导师提示词、原文覆盖、模式内容要求、模型选择或推理强度。项目／对话／设备归属继续各自隔离。

## 受控内存对照

使用两个独立 Python 进程，分别运行修改前的任务调度器快照和当前实现；真实 SQLite、注册任务、状态与重试机制均参与。没有调用外部模型或操作用户学习数据库。

### A. 六项任务挂起等待

每项任务保存两条较长的冻结聊天；被测试的工作协程只等一个事件，不执行模型。因此本组衡量的是**调度器额外保留**，不包含模型工作本身所需的上下文。

| 指标 | 修改前 | 当前 |
|---|---:|---:|
| 等待时 Python 存活分配 | 约 12.69 MiB | 约 0.09 MiB |
| 测量期间 Python 分配峰值 | 约 15.31 MiB | 约 0.11 MiB |
| 等待时单个 Python 进程工作集 | 约 47.99 MiB | 约 34.80 MiB |
| 整个进程峰值工作集 | 约 48.55 MiB | 约 42.95 MiB |

两版六份完整保存参数的哈希均在运行前后保持一致；任务归属和完成状态一致。排队／等待工作没有借机清空真正的学习记录。

### B. 六项失败任务等待自动重试

每项失败调用分配一份真实的 8 MiB 缓冲，并通过异常原因链退出。用弱引用检查这些对象在重试等待期间是否仍存活，模拟长原文／请求等被失败堆栈留住的情形。

| 指标 | 修改前 | 当前 |
|---|---:|---:|
| 仍被失败堆栈保留的 8 MiB 缓冲 | 6 份 | 0 份 |
| 等待时 Python 存活分配 | 约 48.13 MiB | 约 0.11 MiB |
| 测量期间 Python 分配峰值 | 约 48.15 MiB | 约 8.13 MiB |
| 等待时单个 Python 进程工作集 | 约 83.19 MiB | 约 34.71 MiB |
| 整个进程峰值工作集 | 约 83.21 MiB | 约 42.75 MiB |

两版都保存首次失败后的第 1 次重试、上限 5、相同错误和原因；完整任务参数哈希保持。测量后取消本次隔离任务，没有等待人为设置的 300 秒退避。

这些数字是受控调度／异常等待场景，不能写成“全应用内存下降 99%”。真实生成仍需要其原文和上下文，OCR／语音／GPU 引擎和 Chromium 也有各自占用。本轮没有测得真实长视频或云端长文提速。

## 完整输入和功能核验

新增 [上下文与等待专项测试](../tests/test_task_context_memory.py)，**12 项通过**：

- 调度只读归属字段，完整保存参数不变，成功返回值保持；不同项目／对话／设备并行时上下文不混用。
- 退避轮询在禁止读取完整参数／结果列的情况下运行。
- 普通错误、原因链、节点组和异常组的缓冲在退避尚未结束时释放；错误与 HTTP 等待依据、文件操作风险标记保留；永久故障不改成重试。
- 通过原生 DeepSeek 适配器的实际 HTTP JSON 序列化，核对完整冻结聊天、1800 次原文推导及尾部条件均进入生成请求；保存的概览模式、直观与专业风格、英语及 high 推理强度恢复。后来公开聊天未混入。返回使用模拟服务，实际 DOCX 导出并读取确认，不据此宣称真实教学质量通过。
