# 图片任务排队与内存优化验收

2026-10-12—13，源码修改，未重新打包。先从 Windows 通知区托盘完全退出旧版，再双击根目录 [验收最新版.vbs](../验收最新版.vbs)。现有 0.4.2 安装包不包含这轮源码改动。

## 实际发现与修改

之前已经限制图片解码／编码同时最多一个工作器，但各工作器完成后仍会把 JPEG／Base64 请求内容留在异步任务里，接着等模型请求名额。多个不同图片任务排队时，这些已准备的数据会积压。进行中的同图复用仅减少相同图片的重复读取，不能解决不同图片的这类积压。

现在原生 DeepSeek、OpenAI 兼容服务和 Gemini API 使用延后准备的请求：

1. 等模型名额时只保存原图路径、位置、OCR 引用及已经固定的模型／推理设置，不解码、压缩或编码图片。
2. 获得原有模型名额后，才在原有单工作器图片队列里准备并发送。没有新增或重复取得模型名额；全局并行开关、并发上限、前台优先及书库预算继续实际生效。
3. 编码后的内容不挂到排队描述对象上；网络或空响应重试重新准备该次请求。图片内容未变时，每次实际发送的内容一致。
4. 图片准备期间暂停时，允许当前本地工作完成，然后丢弃待发编码、释放模型名额，停在发送之前。继续时从原图重新准备。同项目的其他任务及其他项目可以继续；准备期间取消，也不会把尚未发出的图片请求发出去。
5. 取消异步任务后，原有图片线程仍占用本地准备名额直到真实处理结束，防止下一个任务和尚未结束的解码重叠。
6. 同图复用识别“准备中、尚未发送”和“已经发送”的区别；暂停的准备者不会把其他任务的同图请求永久悬置。已有独立任务、审批和可修改文件的 Agent 调用继续隔离。

仅采用已核对的原生 API 适配器；未知自定义适配器仍接收原来的完整字典请求，避免改变其调用约定。Codex 的原图路径输入和 Gemini CLI 的既有能力没有借此转换成其他接口。

图片数量、来源位置、原有 1280px 缩略策略、JPEG 质量 82、视觉记录规则、讲解风格及模型／推理选择均未降低。完整原文和原始 OCR 的保存方式未改变。

## 实际图片与请求内存对照

在两个独立 Python 进程里对照修改前快照和当前代码：8 批独立图片请求，每批 4 张不同的 1280×1280 PNG，模型并发上限为 2。PNG 为固定随机种子生成的高细节压力样图，叠加文字和公式；真实运行 PNG 读取、JPEG 编码、Base64、HTTP JSON 序列化和传输适配。服务响应使用明确的模拟传输，外部模型调用为 0。

两版都将最先发出的两个请求在模拟服务中保持两秒，以观察其余请求的实际排队状态。压力样例不等于用户整本教材、整段视频或整个 Electron 进程。

| 指标 | 修改前 | 当前 | 范围 |
|---|---:|---:|---|
| 模型运行／排队批数 | 2／6 | 2／6 | 同一并发上限 |
| 队列积压时已经编码的批数 | 8 | 2 | 其余只保留路径及描述 |
| 队列积压时 Python 存活分配 | 约 65.1 MiB | 约 33.5 MiB | 降低约 49% |
| 同时刻单个 Python 进程工作集 | 约 102.9 MiB | 约 71.1 MiB | 降低约 31% |
| 这次压力运行的进程峰值工作集 | 约 120.2 MiB | 约 109.8 MiB | 降低约 9% |
| 这次压力运行的 Python 分配峰值 | 约 91.5 MiB | 约 81.3 MiB | 降低约 11% |

全部 8 份实际请求的模型、推理参数、文字、图片内容和 schema 哈希逐份一致；全部逐图返回记录及位置一致。最终观察记录 SHA-256 为 `11cb8bc9d1bb6214a8fd20614ddf1db2a6537c45c66827247acfb058b70d31f2`。这验证传输内容保持，不是模型教学正确性的评价。

另做一次关闭内存追踪、取消两秒服务保持的短延迟对照：修改前约 2.625 秒，当前约 2.619 秒，基本相当。没有据此宣称提速。带内存追踪的压力运行分别约 4.04／4.79 秒，且包含人为服务保持，不作真实生成速度结论。模型名额现在还包含视觉请求的图片准备时间，“耗时详情”的说明已同步，仍可单独查看图片编码阶段；阶段可能重叠，不能相加。

## 可自行验收

1. 从托盘完全退出旧版，双击根目录源码入口。
2. 在“设置与联动 → 生成偏好 → 任务调度”保留并发上限 2。
3. 安排多份不同扫描资料或视频的独立读取／成果任务。排队的图片不会提前解码成多份大请求；运行状态和排队数量仍显示在任务卡。
4. 在图片准备期间暂停；当前本地处理完成后任务保持暂停，不应继续发出那次视觉模型请求。其他独立任务仍可运行，继续后沿用原图及原设置。
5. 在任务卡点“耗时详情”核对模型名额排队、图片编码与图像复用。手机连接此源码服务后刷新页面即可使用相同后端。

## 剩余限制

这轮证明减少了不同图片任务的排队内存积压，没有证明整机 RAM、完整首次视频解析或云端长文生成的全部问题解决。模型名额等待、完整语音识别、不同画面的 OCR／视觉读取和长文写作仍会耗时。已经保存的识别不会自动重做；暂停已发送的请求依旧先保留其完成结果，再停在安全点。

默认并发 2 仍较合适。继续加大并发会增加已经准入的图片请求、模型上下文和网络响应内存；自动 GPU 转录也可能提高进程工作集。应按实际任务阶段继续定位，而不是只扩大并发或减少来源细节来取得好看的速度数字。
