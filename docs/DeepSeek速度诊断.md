# DeepSeek 速度诊断

2026-10-15。用户询问软件的 token 吞吐是否过慢。此次完成真实测量，新增隔离诊断与报告脚本，没有更改生产模型、网络配置、教学规则或任务默认行为。

## 方法

- 通过软件原生 DeepSeek 流式客户端，与跳过 Agent 状态循环的直接 HTTP 路径对照。每组同一份请求体，发送前按完整 JSON 计算指纹并验证一致。
- 三组：短数学讲解关闭思考、相同短讲解 high、上一轮保存的合成数学核查任务 high。软件／直接 HTTP 次序部分反转，共 6 次真实请求。
- 上述“直接 HTTP”仍使用同一测试环境连接配置，表示绕过 Agent 状态循环；不同于后续网络试验的“直接连接”。软件客户端样本也不包含完整工作台界面和文件处理。
- 另用同一短请求，关闭思考，每次新建连接，顺序 system／direct／direct／system，共 4 次真实请求。
- 记录响应头时间、首个推理片段、首末正文片段、服务返回的输入／生成／推理 token、缓存命中、本机调度排队、上层消费片段计时。缺失的分项保留未知；不按字符猜 token。
- 只保存状态、计时、计数、内容哈希。密钥、请求正文、最终正文和推理正文不写入测速结果；原合成核查材料仍在原开发测试目录，不是读取学生尚未提交的题单。
- 测试读写位于 `build/deepseek-speed-20261015-1` 与 `build/deepseek-connection-speed-20261015-1`，使用前设置独立的数据与语义模型目录。未写生产设置或用户学习记录。

## 结果

| 任务 | 路径 | 总耗时 | 推理 token | 正文 token（服务分项可得时） |
|---|---|---:|---:|---:|
| 短讲解，思考关闭 | 软件 | 16.77 秒 | 未单列 | 未单列；生成总数 217 |
| 短讲解，思考关闭 | 直接 HTTP | 2.02 秒 | 未单列 | 未单列；生成总数 186 |
| 短讲解，high | 直接 HTTP | 14.15 秒 | 1348 | 225 |
| 短讲解，high | 软件 | 12.18 秒 | 1658 | 273 |
| 核查任务，high | 软件 | 60.82 秒 | 7406 | 17 |
| 核查任务，high | 直接 HTTP | 42.80 秒 | 7078 | 17 |

软件路径的核查最终正文为 52 字符，但实际生成 7423 token，推理占约 99.77%。从发送到首个推理片段约 15.67 秒，随后到首个正文片段约 45.01 秒，正文片段窗口约 0.03 秒；软件名额排队约 0.018 秒。

长核查包含推理的输出接收速率约 165–170 token/秒，是服务报告生成 token 数除以首末生成片段到达时间；不能当服务端纯计算吞吐。17 个正文 token 的窗口太短，不用它单独评估速度。上层消费片段计时约 0.05 秒，不含网络等待和全部协议解析；它没有显示逐片段消费占去几十秒。

长核查的两次总耗时不能直接归因于客户端差异：软件／直接 HTTP 的输入缓存命中分别为 256／3584 token，响应头等待分别约 15.32／0.56 秒，生成的推理 token 量也不同。短 high 组软件路径反而更快。每格仅一次，不做稳定的两客户端速度排名。

四次新连接的总耗时依次为 4.37／2.08／2.49／4.48 秒。system 平均 4.42 秒、direct 平均 2.29 秒；响应头等待均值分别约 2.90 与 0.49 秒。本次进程存在环境代理，而 Windows 用户／系统级 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY 环境变量均未设置。它不能证明普通桌面启动的软件继承了相同代理，也不能排除 Windows 其他代理配置；不据此改生产网络。

十次请求全部成功、无重试，服务报告输入＋生成总数为 28935 token，包含缓存记录，不直接折算费用。保存前核验每项总数等于输入与生成之和。

## 判断与改进优先级

1. 当前证据更支持“高推理生成量较大＋多轮调用＋响应前等待”，未显示软件客户端把 token 消费降到很低水平。不能用最终正文长度估计模型已经生成的总量。
2. 先评估合并重叠核查或分配不同推理预算能否保留质量；本轮是速度诊断，没有据此降低教学模型的默认强度或减少审查。
3. 后续任务记录宜增加逐请求 usage 与首字等待。当前新文件是独立诊断工具，不是已经集成的实时 token 仪表。历史 118 秒请求没有这些分项，本次补测不能反推其内部细节。
4. DeepSeek 协议兼容别名 medium／high／xhigh 都映射到 high；改变兼容标签不一定改变速度。“快速审查”与模型推理档位也独立，快速＋high 仍可能长时间思考。

服务 usage 字段定义核对 [DeepSeek 官方 Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/)：`completion_tokens` 为生成数量，`completion_tokens_details.reasoning_tokens` 是其中推理数量，流末尾返回 usage。本机响应头时间包含连接、代理、传输、服务端等待及输入处理等因素，无法凭此单独分离。

## 验收与打开

- `tests/test_speed_probe.py` 的 8 项专项检查通过：时间窗口、缺失用量、单片段、无效计数、原生／直接请求一致、错误保留及隐私边界。真实接口返回另作验证，不把受控响应当真实性能。
- `scripts/build_speed_diagnosis_report.py` 校验十次请求、三组请求指纹、四次连接请求指纹、服务用量等式及客户端／协议／调度源码与测速前指纹一致。
- 可打开 `build/deepseek-speed-review-20261015/DeepSeek实际速度诊断.html`；同目录有六次主试验的指标 CSV 和最终核验 JSON。页面不引用远程资源，官方文档仅为点击链接。

尚未测试全工作流、繁忙并发、长视频／OCR／转录、整体 RAM、真实安卓和 DeepSeek 网页端。缓存、随机生成长度、首连接与服务状态未固定，不能据此承诺普遍提速或统计上的显著差异。本轮没有打包。
