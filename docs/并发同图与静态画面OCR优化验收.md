# 并发同图与静态画面 OCR 优化验收

2026-10-12。继续减少图像任务重复处理，保留教学提示词、讲解／审查／推理设置、完整原文、视频转录和采样位置。本轮为源码更新，未重新打包。

## 同时首次核对相同图片

原来两项任务在缓存尚未填充时会各自编码、调用模型，完成后才复用缓存。现在原生 DeepSeek、继承原生图片读取的兼容接口及 Gemini 使用小型进行中请求协调器：

- 实际服务适配器、地址、画面模型、推理设置、账号、项目、原图文件字节、位置及 OCR 全部相同，才复用客观核对结果。批次内的图片 ID 不影响身份，结果映射回各任务自己的 ID。
- 两批部分重叠时，先处理自己负责的新图片，再等待重叠图片，避免各持一张图互相等待。仍使用相同视觉规则及图像编码质量；没有把画面识别改成讲解，也没有把上下文、批改答案或学生掌握情况共享出去。
- 只有原生、固定提示词、没有工具调用的图片方法接入。Codex Agent、聊天、可修改文件的工具及未知适配器不通过这个协调器合并，审批在各自任务中处理。
- 等待者不占额外模型名额。取消一个等待者不会取消生产任务或其他等待者；生产者失败／取消时，其他任务接手读取，不把生产者的错误当成图像观察。
- 尚未开始、被暂停或因后台优先级而等待的生产者，不拦住需要继续的独立任务。已经进入处理的请求允许先完成再安全暂停。暂停的等待任务保存完成步骤，继续不重发已完成步骤。
- 首次核对与收到共享结果后检查原图 SHA-256；图片在过程中变更不能作为有效的旧图结果返回。进行中登记最多 128 张，每份共享观察最多 32,000 字符；表中只保存哈希、任务步骤与 Future，不保存 PNG、Base64 或聊天正文。达到上限就独立处理，仍遵守现有图像与模型队列。

原生请求依然属于发起者的任务。暂停导致另一任务接手时，原任务随后恢复可能产生重复核对；这是避免一个暂停任务堵住其他任务的选择，没有承诺任何时序下绝无重复请求。部分图像返回缺失时仍逐图补读；不以批次成功掩盖漏图。

来源读取的并行工作者现在在整个读取被取消或异常退出时一并清理，避免兄弟图片请求在已结束任务后继续运行。这个清理没有关闭用户的其他任务或应用。

## 视频相同画面的本机 OCR

视频采样与时间戳算法保持。每次视频解析仅保留上一张成功 OCR 的文件 SHA-256 和文字；下一个实际参与 OCR 的 PNG 文件字节完全相同时，复用文字。一个像素／文件字节不同就重新识别。不以缩略图的“看起来相似”跳过识别。

- 采样画面仍按原规则保留，包括原本的定时复访；源时间戳、文字、顺序及全文转录不缩减。
- OCR 失败不复用，下一张相同画面可重新尝试；空字符串可以是成功的无文字画面。文字超过 32,000 字符不保留在这个临时复用器。
- 每次解析有自己的复用器，不在不同视频之间交换 OCR；只保留一份小文本，不保留历史图像数组或另一份推理模型。
- `video_sampling` 保留原 `ocr_frames` 计数，新增 `ocr_requests` 和 `ocr_reused_frames`，区分参与核对的画面与实际本机识别次数。

这不会加速没有完全相同画面的视频。音频识别模型、beam size、VAD、完整音轨和采样间隔未降低；本轮没有改变语音识别的实际解码速度。

## 两端显示

“成果文档／任务 → 耗时详情”在图片复用卡片中单独显示“复用其他进行中任务的同图核对”；它不混入内存／磁盘命中计数。需要新核对的计数排除实际收到的有效共享观察。

发生等待时记录来源正文以外的 `vision_wait` 时间；阶段可以重叠，不能简单加成任务总时间。不同任务可能各负责部分图片、互相复用另一部分，不应期待其中一项永远承担全部调用。

手机页面缓存更新到 v31，操作指南补充同图复用、暂停／取消边界和静态视频的适用范围。

## 修改前后证据

### 冷图片并发

在分别启动的 Python 进程中载入保留的旧 AI 模块与当前模块；两个任务同时读取相同的 12 张 1280×720 PNG，模型并发上限 2。每个明确模拟的模型请求等待 120 ms，保持编码策略、输入 OCR 和观察文本相同。计时三轮，Python 临时分配另行测量；计时期间没有同时运行 OCR 或其他测试。

| 受控场景 | 修改前 | 修改后 |
|---|---:|---:|
| 两个任务合计模型请求 | 6 | 3 |
| 实际编码的图片合计 | 24 | 12 |
| 三轮平均耗时 | 910.21 ms | 616.61 ms |
| 临时 Python 峰值 | 466,357 B | 467,194 B |

完成原生适配器白名单收紧后重新以独立进程核对，最终平均耗时约减少 32.3%。这次临时 Python 峰值增加 837 B，基本相当；较早复跑也有约 7KB 的增加。这种小差异不应被当成明确的内存收益；协调器以小型登记减少重复编码和云端请求。Python 测量也不包含全部 Pillow／ONNX 原生内存或整机 RAM。

完整原文、观察与位置输出 SHA-256 一致：`670958a0929c1bead707911da59b8206e089343bc396f3b1a246b7683f555d88`。外部模型请求 0。记录见 [冷并发对照](../build/vision-concurrent-20261012/cold-comparison.json)，可复跑脚本 `scripts/benchmark_vision_concurrent.py`；旧模块保留在该记录目录。这些模拟时间不代表真实 DeepSeek、整段视频或完整讲解 DOCX 的降幅。

### 实际本机 OCR

从之前本地实际视频抽帧测试中选一张真实课程 PNG，复制为 8 份完全相同的文件，使用同一个已加载的 RapidOCR CPU 引擎、4 个 CPU 线程及原识别参数。

| 8 份完全相同课程画面的 OCR | 修改前 | 修改后 |
|---|---:|---:|
| 实际识别次数 | 8 | 1 |
| 完整文字 | 536 字符 | 相同 536 字符 |
| 实测耗时 | 19.06 秒 | 1.98 秒 |

此静态重复样例耗时约减少 89.6%，原文字逐字符相同；未重新人工验证全部文字正确性。记录见 [实际 OCR 对照](../build/vision-concurrent-20261012/exact-ocr-comparison.json)、[原识别文字](../build/vision-concurrent-20261012/exact-ocr-text.txt)。脚本 `scripts/benchmark_exact_frame_ocr.py` 不修改原视频。它是同一课程画面的重复副本试验，未重新解析整段课程，也不能套用于含持续字幕、笔迹变化或其他动态内容的视频。

## 当前边界与后续判断

本轮没有声称扫描书库全部性能、完整视频总耗时、所有 AI 教学质量或软件总 RAM 已解决。单个视频的主要开销仍可能来自完整语音解码、每张变化画面的 OCR、模型推理与长文写作；应依据真实任务“耗时详情”继续判断。不能仅靠删除讲解细节、减少原文或降低推理强度来凑提速数字。

运行源码：彻底退出旧 StudyForge 托盘进程后，双击工作区根目录 `验收最新版.vbs`。旧 0.4.2 安装包不包含本轮源码。隔离测试没有修改用户日常学习数据库，所有本轮界面测试服务在验收后停止。
