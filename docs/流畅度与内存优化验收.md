# 流畅度与内存优化：修复内容、实测与范围

2026-10-10，源码交付。双击 [验收最新版.vbs](../验收最新版.vbs) 使用；先从托盘彻底退出旧版。手机刷新对应源码版页面。现有安装版 0.4.1 没有自动包含这轮源码修改。

## 核查结论

之前的优化已经包含完整解析复用、视觉请求分批与缓存、共享 OCR/语音引擎、后台让位和语义模型释放。它们解决了一部分重复计算与多实例内存问题；不能据此宣称整款软件已经流畅。

这次继续定位并修复了四条实际路径：

1. **长回答反复重排。** 桌面流式输出每次重新解析全部 Markdown，重新构造整段 DOM 和全部公式；手机同样会重排。现在保留未变的 Markdown 块及已排好的公式，只更新发生变化的后缀。仍重新检查全文语法，所以列表、表格、尚未闭合的代码和后置引用定义可以正确变化。替换回答、修改公式、恢复已保存正文时正确失效。
2. **图片编码阻塞服务。** 视觉资料压缩原来直接运行在异步服务主线程；现在进入独立、有界的本地准备队列，最多一个解码/编码任务。网络模型请求继续使用原有并发上限，不把整份生成任务串行化。取消后，真实编码线程结束才释放资源位置。
3. **大图多一份完整像素副本。** RGB 图片转换到 RGB 原来会产生无用的全分辨率副本。现在在原 RGB 图像上缩放。保持原来的 1280px 缩略策略、JPEG 质量 82；RGBA、灰度等图像保留原转换路径。
4. **缓慢响应造成刷新积压。** 工作区与调度轮询合并在途请求；书库自动轮询不会在慢请求后排出一串待执行刷新。手动操作后的刷新仍会取得新的结果。目录状态只读取需要的阅读元数据，不每隔两秒载入各版本完整笔记。

同时修复一个取消任务的故障：本地任务记录只有项目 ID，但书库取消逻辑按包含 job_id 的对象读取，原生处理在途时可能报错。现在保存完整的归属元数据，取消等待本任务的真实本地处理结束，不等待无关项目。

## 真实 Chromium 渲染测量

自编约 23,792 字符、100 个含公式推理段落，逐次追加，共 80 次更新。基线与优化在同一 Chromium 运行环境按前后交错顺序各测两遍，每遍开始前收集垃圾；包含渲染后的实际布局读取。

| 指标 | 原实现 | 优化后 |
|---|---:|---:|
| 80 次更新的平均累计渲染耗时 | 6,764.65 ms | 578.85 ms |
| 每遍最慢一次更新的平均耗时 | 186.65 ms | 11.05 ms |
| 测量的 JS＋嵌入堆峰值平均值 | 约 347.94 MiB | 约 74.39 MiB |

该样例渲染耗时减少约 **91.4%**，测量堆峰值减少约 **78.6%**。这不是整个 Electron 应用的工作集，也不是 AI 生成速度；公式密集程度和答案长度会影响结果。

另有 **108 次正文等价检查**，对照改造前的真实渲染函数：分段追加、公式改写、引用块、编号与嵌套列表、表格、代码围栏、后置链接定义、占位符碰撞、未闭合语法和恢复后的追加。检查 HTML 结果一致，并验证未变段落的真实 DOM 节点保留。手机采用同一套 Markdown/公式渲染，原始 HTML 按正文文本显示，不执行模型输出的 HTML。

记录：[渲染负载与等价检查](../build/ui-performance-20261010-1/report.json)。可通过 `scripts/benchmark_stream_render.js` 复现，基线文件保存在同一隔离目录。

## 真实大图准备测量

两份独立 Python 进程使用同一 4000×6000 RGB 样图，各准备四份实际视觉请求编码。基线保留原转换流程，优化走软件的真实编码函数。

| 指标 | 原实现 | 优化后 |
|---|---:|---:|
| 单个进程工作集峰值 | 248.90 MiB | 157.25 MiB |
| 四张图的累计准备耗时 | 0.781 s | 0.546 s |

该样例进程峰值减少约 **36.8%**，准备耗时减少约 **30.0%**。四份实际编码 SHA-256 完全相同；专项回归还逐字节核对 RGB、RGBA、灰度输出。不是通过降低图像质量或减少抽样画面取得的结果。

记录：[基线](../build/vision-preparation-20261010-1/baseline.json)、[优化后](../build/vision-preparation-20261010-1/optimized.json)。这是图片准备进程的实测，不包含模型、OCR、全文转录或全应用内存。
