# 聊天审批悬置与续接验收

日期：2026-10-07。修改已进入源码验收版。

## 原因

聊天入口创建的 `AgentRuntime` 没有设置 `on_event`，也没有后台任务 ID。权限执行器将它判断为不能与用户交互的调用方，创建审批记录后立即返回 `PermissionError`。模型收到这个工具失败结果后完成回复，留下一个已经没有等待者的审批卡片。点击卡片只能改变记录，无法续接已结束的工具调用。

之前的权限验收直接创建带回调的工具执行器，验证了单次授权规则，却没有覆盖从真实聊天发送入口到模型工具调用的整条流程。

## 修改

- 聊天流接入工具事件转发，工具审批期间保留原模型轮次和原指令；审批通知能在工具调用等待时即时送达界面。
- 审批期间不返回“未授权”作为工具结果，不发布最终助手消息。用户批准后，同一次工具调用继续执行，再把实际结果交回模型完成回复。
- Codex 的模型响应超时只计算实际运行时间，排除等待用户审批的时间；没有模型响应且不再等待审批时，原响应超时仍然有效。
- 待审批状态绑定实际操作 ID，迟到的模型进度通知不能将正在等待的审批改为“进行中”或解除等待。
- 界面显示“等待你审批 · 批准后自动继续原指令”；切换对话后保留原回复的等待状态，回到该对话可以继续审批。
- 已成功批准或拒绝的审批卡片不会被迟到的轮询响应重新显示。
- 不能交互的调用方在创建审批记录前就拒绝操作，避免产生没有等待者的卡片。
- 取消聊天时取消对应审批和工具等待，清理事件转发任务；被取消的审批无法再批准。现有文件状态校验、单次授权、项目及对话归属校验保持生效。
- 导师工具提示词明确区分等待审批与用户拒绝；批准后继续原指令。

## 验证

### 后端回归

165 项相关 Python 回归通过，涵盖聊天、Codex / DeepSeek 工具协议、权限、并发、取消、生成暂停、对话隔离和退出恢复。最后补修操作 ID 后，28 项审批与共享对话相关复核通过。测试出现一项现有 Starlette TestClient 的弃用提示。

新增回归覆盖：

- DeepSeek 和 Codex 审批前没有文件变更、没有最终助手消息，也不发起后续模型请求或提前确认工具结果。
- 批准后同一次回复完成，只保存一条原用户指令和一条最终回复，无需重新提交指令。
- 拒绝后保留文件，导师收到真实拒绝结果。
- 一次指令中的读取和写入分别等待自己的审批。
- 等待时间超过模拟 Codex 响应超时仍保持悬置；审批结束后模型真正停止响应仍会超时。
- 中途取消、没有交互入口，以及事件队列已满时取消的清理。

### 实际 Electron 窗口

通过真实聊天发送按钮启动生产聊天接口，通过真实鼠标点击批准或拒绝；模型及 Codex 连接使用协议替身。

- DeepSeek：等待 1.8 秒，原文件未变，最终回复尚未保存；点击批准后自动完成。
- 拒绝修改后原文件保持不变。
- 连续两个文件操作逐次审批，第二个操作在第二次批准前不执行。
- Codex：模拟模型响应超时为 0.4 秒，等待审批 2 秒后仍保持悬置，没有提前发送工具结果；批准后自动完成，拒绝后保留原文件。
- 待审批期间可以切换对话并完成另一段回复；回到原对话后继续审批。
- 实际模型并发上限设为 1，其他对话仍可回复，确认审批等待已释放模型名额。

结果：11 次模拟服务请求，**付费模型调用 0 次，控制台错误 0 条**。本项确认应用控制流程，没有对真实供应商模型的任意答复作保证。

## 打开与验收

从 Windows 托盘完全退出正在运行的旧版，双击根目录 [验收最新版.vbs](../验收最新版.vbs)。这次修改尚未重新打包，旧 0.3.5 安装包不包含修复。

选择“需要审批”，让导师修改一个未加入可修改目录的测试文件。看到卡片后暂不批准：回复应持续显示等待，文件保持不变；批准后自动续接，拒绝后不执行该操作。

旧版已经结束的失败回复没有可续接的执行过程。启动新版后重新发送该条失败指令一次；新的审批请求按上述等待与续接流程执行。软件完全退出或重启会让旧审批失效，避免重启后执行过期文件操作。
